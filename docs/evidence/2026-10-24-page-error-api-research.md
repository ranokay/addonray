# Page-error API research

Documentation/source review and preliminary fixture evidence on 2026-10-24 for the [page-error interview](../decisions.md#page-error-diagnostic-interview). The user selected broken-page troubleshooting, counts-only results for two JavaScript event kinds, a current-document observation, separate check tabs, a 30-second/200-event limit, manual Stop, and one final summary/reset per attempt. The user accepted Firefox isolated execution and Chrome page-side execution. The user subsequently approved the concrete feasibility-first implementation scope and budgets. Documentation findings and observed fixture results are separated below; neither establishes product qualification. Implementation is not approved.

## Future observations and visibility

Window `error` and `unhandledrejection` are event notifications. Neither reviewed `scripting.executeScript` contract documents retrospective console/error retrieval. The planning inference is that this collector needs an explicitly started observation interval, rather than a historical snapshot like the existing load timings. This is an API-contract inference, not an observed browser result. See [Window error](https://developer.mozilla.org/en-US/docs/Web/API/Window/error_event), [unhandled rejection](https://developer.mozilla.org/en-US/docs/Web/API/Window/unhandledrejection_event), and [Firefox executeScript](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/scripting/executeScript).

Uncaught JavaScript error notifications and promise rejections that are unhandled when observed are separate event kinds. A later rejection handler does not undo the earlier notification. Handled exceptions, arbitrary `console.error()` calls, the browser console feed, and failed resource loads are separate mechanisms. Element load errors do not bubble and need a separate classification design. Do not imply that these two JavaScript notifications cover all broken-page failures. See [element error](https://developer.mozilla.org/en-US/docs/Web/API/HTMLElement/error_event).

Chromium's moving source filters [promise-rejection dispatch](https://raw.githubusercontent.com/chromium/chromium/main/third_party/blink/renderer/core/events/promise_rejection_event.cc) to the creator's JavaScript world. Its [ErrorEvent implementation](https://raw.githubusercontent.com/chromium/chromium/main/third_party/blink/renderer/core/events/error_event.cc) also has an execution-world filter. An isolated content-script listener must not be assumed to observe ordinary page-script events. Moving source does not establish the pinned Chrome 156 behavior. Firefox's [content-script isolation documentation](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Content_scripts#content_script_environment) describes a separate global and Xray wrappers, without settling the proposed event visibility. Controlled tests must compare isolated and page-world observations on each pinned browser.

## Page-world and privacy boundary

Current [execution-world documentation](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/scripting/ExecutionWorld) and [compatibility data](https://raw.githubusercontent.com/mdn/browser-compat-data/main/webextensions/api/scripting.json) list MAIN support from Firefox 128 and Chrome 102, within AddonRay's existing minima. MAIN shares the page's JavaScript environment and lacks content-script-only extension APIs. The page can inspect or interfere with injected logic; results remain untrusted observations. Counts alone cannot prevent suppression or manufactured apparent observations. Chrome also documents [page CSP applying in MAIN](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts#content-security-policy). API availability does not establish this collector's feasibility or authorize a new page-world integration.

The existing `activeTab` and optional `scripting` permissions can authorize injection into an eligible selected page. This does not justify host grants, persistent content scripts, or broader permissions. Existing protected-page restrictions still apply. See [injection permissions](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/scripting/executeScript).

The accepted counts-only boundary excludes raw messages, stacks, script filenames, URLs, rejected values, and retained event objects. [ErrorEvent fields](https://developer.mozilla.org/en-US/docs/Web/API/ErrorEvent) can contain sensitive text and arbitrary error values; a [rejection reason](https://developer.mozilla.org/en-US/docs/Web/API/PromiseRejectionEvent/reason) can be any JavaScript value. A minimized collector should avoid reading or serializing those fields. Cross-origin restrictions can hide notifications or details, so zero observed events cannot establish an error-free page. See [rejection disclosure restrictions](https://developer.mozilla.org/en-US/docs/Web/API/Window/unhandledrejection_event#usage_notes).

## Lifecycle facts and unresolved decisions

A toolbar popup closes when the user moves focus to interact with the page. Its existing memory lifetime cannot silently become a longer observation session. The interview must choose a visible owner, deliberate source selection, results retention, cancellation, and close/reload behavior before implementation.

Already injected code needs its own cleanup; unregistering a content script does not remove that code. Permission revocation alone is not evidence that a listener stopped. Browser timers can run later than requested, especially in inactive tabs, so a requested duration is not automatically an exact cleanup deadline. See [Chrome scripting](https://developer.chrome.com/docs/extensions/reference/api/scripting) and [timer delays](https://developer.mozilla.org/en-US/docs/Web/API/Window/setTimeout#reasons_for_delays_longer_than_specified).

Firefox's temporary page grant can end on a new document, while Chrome can retain it across a same-origin reload. The proposed first collector must define document changes independently of whether a permission remains granted. See [Firefox activeTab lifetime](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/activeTab_permission#when_access_is_revoked) and the existing [timing-comparison evidence](2026-10-24-phase2-timing-comparison.md).

The user subsequently settled current-document future observation, the two event kinds, separate check-tab ownership, a 30-second/200-event limit, Stop retaining confirmed partial counts, and one final summary per attempt. Reload/navigation/source failure means interrupted/unavailable rather than fabricated zero counts. Start over erases the result before another explicit Start on the original source tab. The world split and final scope/budgets are accepted in the [plan](../plans/phase2-page-errors.md). Do not reuse the timing collector's measured budget as evidence for an unimplemented error collector.

## Essential lifecycle feasibility

Before product wiring, a second named fixture passed all 13 lifecycle checks on each of the same four macOS arm64 browsers. Its manifest used activeTab plus optional management/scripting, without host permissions. The actual toolbar action supplied the temporary source grant. This was source/control feasibility, not the shipped product or native consent/usability qualification. Every report records dirty source `93f938e`, exact browser/driver versions, the candidate source hash, and successful browser/server cleanup.

The candidate source SHA-256 is `79bb3cb712a2fbbf51328ef604074ed3073a62c41cb459ef592cbf05569dedb7`. Raw lifecycle reports and the authoritative filenames are listed in ignored `.scratch/page-error-feasibility/lifecycle-summary.json`. Checks covered inactive-tab binding, explicit Start, selected-world control, confirmed Stop, discard, actual optional scripting revocation, owner reload/close, early closure before delayed Chrome MAIN installation, source navigation/closure, top-frame exclusion and restrictive CSP. Fixture-only numeric DOM markers confirmed listener removal by checking physical callbacks against subsequent page-owned events. A successful zero alone was not cleanup evidence.

The real 200-event cap stopped during 202 generated events on all four targets. The real 30-second window returned observedMs 30000, with wall durations of 30066, 30133, 30141 and 30227 ms respectively. A deliberately blocked thread confirmed that events reaching their callback after the monotonic deadline could not increase counts before a delayed timer. These observations do not promise an exact cleanup instant.

Chrome's full sequence obtained a genuine persisted BFCache restoration without resumed observation. Firefox's full multi-frame sequence did not. Separate focused single-frame runs on all three Firefox versions obtained genuine restoration for both a clean positive control and an active candidate that ended on leaving. After restoration, later events did not increase the ended callback markers and the owner retained no result. These focused runs used normal history/BFCache preferences without overrides. The reason the full Firefox sequence was not cached remains unknown, and stopped-before-leave variants that reloaded do not establish a cause.

Independent read-only review examined the runner assertions, all four lifecycle reports and all three focused Firefox reports. No material prerequisite remained open within this declared candidate scope. The reviewer distinguished the candidate from production and required late-Stop timeout mapping in production. Deterministic production tests now cover that mapping.

Production integration, production overhead, unmodified native launch/consent/usability, hosted OS checks, private/unknown contexts, hostile-page behavior, crash/discard and transport-loss cases require separate evidence. The source fixture's owner and validator were not reused as product implementations.
