# Firefox feasibility evidence

Observed on 2026-10-22 using Firefox 158.0.1, macOS arm64, and Selenium WebDriver 4.51.0. The browser ran headlessly in a disposable profile. All installed add-ons in the test were controlled fixtures or this production build. No ordinary browser profile or user-installed extension was inspected or changed.

## Observed checks

1. The actual production popup document starts without collecting inventory.
2. Denying the real optional `management` permission leaves inventory empty and produces the denial message.
3. Approving that prompt lets the production interface display the controlled inventory.
4. Clear removes results. Refreshing a populated production document starts empty.
5. Revoking `management` clears the production inventory through Firefox's actual permission event.
6. Opening AddonRay through Firefox's real toolbar action grants its production extension selected-tab access. A subsequent API call from that same extension can inspect the controlled local tab without host permissions. This tests the browser grant, not the full popup interaction.
7. The enabled ordinary fixture reports its declared `storage` permission.
8. After the test driver disables that controlled fixture, Firefox omits its API and host permission metadata. The fixture still appears as disabled.
9. The ordinary WebExtension `setEnabled` attempt to enable that fixture is rejected. Its disabled state remains unchanged.
10. A test-only harness can inject into the loaded local HTTP fixture. A page-world marker exists, while the default isolated world cannot see that page global. Supported performance entry types are observed as browser support data.
11. `about:addons` provides no usable injection result and contains no test injection marker.
12. The loaded AMO page provides no usable injection result and contains no test injection marker.

The `about:addons` check resolved with unusable frame results, while AMO rejected the promise. A fulfilled API promise alone does not prove successful injection.

## Evidence boundaries

The production popup document was opened in a browser tab for consent and inventory tests. The test driver automated Firefox's real permission dialog decisions through its browser-UI context. Full native-popup consent, focus, and lifetime behavior remains untested. The actual toolbar action grant was checked separately, with no added product permissions.

The isolation and restricted-page contract probes use a separate temporary harness with `management`, `scripting`, `tabs`, and broad host access. These permissions never enter the product manifest. Results from that harness do not qualify the product's interactive page-probe adapter by themselves. The product adapter and cancellation behavior have separate simulated tests.

The driver changes only the known disposable ordinary fixture, through privileged test setup. Product code never calls `management.setEnabled`. The enterprise-policy exception was not tested.

This run qualifies neither the manifest minimum Firefox 140, an ESR version, Windows, Linux, Android, nor Chromium. No performance overhead, general conflict detection, or per-extension attribution claim follows from these probes.

## Reproduce and bind to a revision

Run `mise run test-firefox`. The task rebuilds the production artifact first, reports each observed check, and records browser version, OS, source commit, dirty status, outcomes, and gaps in `.scratch/firefox-evidence.json`. A run before the initial commit has no source commit and is explicitly marked dirty. Use a clean committed checkout when you need revision-bound evidence.

Raw screenshots and generated fixtures stay in `.scratch/`. This document is the durable sanitized account of observed behavior. It is not a certification of untested environments.
