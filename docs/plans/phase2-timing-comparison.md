# Phase 2 optional timing comparisons

Status: approved for implementation, tests, independent review, and signed private delivery on 2026-10-23. The user confirmed this concrete plan after answering all six product questions in the [interview](../decisions.md#timing-comparison-interview). Production qualification remains incomplete until the checks below have observed evidence.

Independent planning review found no material issue in scope, ownership, selection, cancellation, or the scratch-evidence claims. It requested explicit context-guard tests and accurate Bun retry wording, now included below. The reviewer read the plan, source, and raw reports without executing tests or browsers.

## Problem and result

The popup displays three loading milestones, but closing it discards them. An investigation retains two inventory snapshots and a manual page assessment without measured page observations. Add optional timing attachments to that existing investigation, using the popup's deliberate page capture and an explicit choice of destination and side.

Inventory captures and timing attachments are separate observations. They need not describe identical browser conditions. Matching the source tab does not verify the page, URL, document, reload, cache state, extension execution, or cause of a difference. Keep the user's page assessment independent of measured values.

## User flow

1. Open a fresh investigation and capture its Before inventory through the existing consent action. Inventory-only comparisons remain available.
2. For a timing comparison, return to the page, open AddonRay's actual toolbar popup, and deliberately inspect the page through the existing scripting consent path. Opening the popup never captures or attaches anything.
3. Choose Attach timing, then explicitly choose a loaded investigation and its eligible Before side. Show a synthetic investigation label without reading another investigation's observations. Confirm the attachment. No destination or side is selected automatically, including when only one is available.
4. The chosen investigation retains its own copy of the three timing measurements and the numeric source-tab ID. The popup continues showing its local result. Its capture can be attached successfully only once; another attachment requires another deliberate page capture.
5. Make a manual change through browser controls and retest or reload the page yourself. Return to the investigation and capture its After inventory. Before timing must already be attached if this attempt will include a timing comparison.
6. Return to that same source tab, open the toolbar popup again, and explicitly capture and attach After timing to the same investigation. This flow renews temporary page access on Firefox after a reload. AddonRay never reloads or changes extensions itself.
7. Compare Before and After values for the three milestones. Show After minus Before in milliseconds only when both values are measured. Positive means a later recorded milestone, negative means an earlier milestone. These observations do not prove an extension caused a change. No automatic assessment, percentage, score, or ranking is produced.
8. Start over removes the inventories, timings, source-tab ID, assessment, selection identity, and pending work. Closing, reloading, or unloading the investigation loses them too. Clearing or closing the popup removes only its own state; an explicitly accepted attachment remains with its investigation.

## Implementation boundaries

Extend the current page-capture result owner to keep the source tab ID beside its validated observation, outside page-provided data. Reuse the self-contained collector and three-measurement contract. Keep measurement differences pure and separate from UI and browser access. Add optional timing slots and source binding to the existing investigation owner without changing its inventory-difference logic.

Use a small extension-view adapter around `extension.getViews`. Each loaded investigation exposes an internal endpoint with a fresh opaque document identity and a reset generation. Discover only own packaged investigation views, returning copied primitive metadata. Resolve the selected endpoint immediately before attachment. A receiver checks the current popup view and route, copies and validates input in its own realm, and rechecks identity/generation/eligibility after any permission lookup before committing. Convert dead-object and cross-view access exceptions to bounded failures. Handle the acknowledgment in the popup's own realm too.

Do not retain a Window or receiver reference between user actions, or insert identities into the investigation URL. The direct call is an internal extension integration. Same-extension views share a trust domain; the sender/route checks limit product entry points, not a sandbox against compromised extension code. Discovery can refresh after an explicit user action; do not install polling or cross-tab monitoring.

Both the popup capture and destination generation must remain current at commit. Keep a busy guard and a consumed marker per popup capture. Reject a pending Before attachment once After inventory capture starts. Ordinary failed transfers leave valid destination data alone. A permission revocation resets the investigation and invalidates pending receivers independently of popup cleanup.

## API feasibility and evidence limits

Scratch research at `2ff84207d96b1c6c25094428231aa643b3d9efcb` with dirty interview documentation passed 11 checks on each of Firefox 140.0, 153.5.1esr reported as 153.5.1, Firefox 158.0.1, and Chrome for Testing 156.0.8078.47/macOS arm64. Drivers were geckodriver 0.37.1 and matching ChromeDriver 156.0.8078.47. All four reports record browser/server cleanup. Raw reports and fixture-generation source remain under ignored `.scratch/timing-handoff-*`.

The candidate used the product's permission budget, with no background, storage, host grant, or registered content script. Its actual toolbar popup discovered two own packaged documents and delivered a synthetic timing block only to the selected one. Receivers rejected tested non-popup, content-script, web, and external senders. Reloaded/closed destination handling and destination-owned timing copies survived the tested lifecycle. The candidate is not the production React UI or packaged AddonRay artifact.

Initial Firefox trials exposed popup-owned acknowledgment data and a retained stale endpoint as dead objects after closure/reload. Final fixtures copied acknowledgment data into the receiving realm and caught stale cross-view access. Keep both failures and corrections in the later evidence record; they establish implementation requirements, not a product defect already fixed.

A real toolbar invocation granted source access in all four targets without host access. A same-origin page reload removed access on all three Firefox versions; Chrome retained it. Reopening the toolbar restored access on each. Research collected through a same-extension control document after that grant and automatically ran a driver-preselected synthetic handoff in its fixture popup. It does not qualify production automatic collection, optional-consent usability, or a human capture/select/confirm interaction.

The scratch orchestration used Node 26.12.1 after the pinned Bun process stalled before module evaluation. Node's built-in TypeScript stripping loaded the existing collector; the project toolchain was unchanged. A subsequent diagnosis could not reproduce the stall: eight bounded trials passed revision checks, JavaScript evaluation in repository/empty directories, the toolchain guard, and real native formatting. The cause remains unknown. The retried shared gate passed with the existing pin, including all 134 baseline tests and 384 assertions. Its dirty planning receipt is `20261023T191728Z-bbcfd15430c6.json`; it does not qualify the unimplemented comparison. No collector overhead was requalified by the scratch research.

Generation/reset races, current permission checks at acceptance, the approved sequencing/source binding, production packaging, and native human use still need implementation evidence. Private/incognito contexts are not qualified by these fixtures and must not be advertised as supported. Native Linux/Windows UI, native minimum/ESR timing flows, full accessibility/screen-reader review, retail Chrome, signed distribution, store submission, other browsers/manifests, and broader hostile-code analysis remain open.

## Qualification and delivery sequence

1. Retain the selected Bun pin and the successful gate retry evidence without claiming the startup cause is known. Obtain final shared-understanding confirmation on this plan.
2. Implement the narrow state/validation/difference behavior with focused tests, then the own-view adapter and deliberate popup/investigation UI. Keep separate fake-browser, scratch-feasibility, and product evidence.
3. Extend durable probes for the production integration and its race/lifetime boundaries. Run focused development checks, independent product/probe reviews, and the shared gate. Fix material findings.
4. Make a signed implementation commit. Run clean source rebuilds and exact pinned macOS Firefox/Chrome checks. Observe actual native UI on available targets; preserve unobserved gates.
5. Push privately. Inspect all six Firefox and both Chrome hosted jobs and their reports for exact source, versions, artifact/rebuild identity, budgets, and cleanup. Record dated evidence and update status; sign/push evidence and verify its final-head checks.

Stop after this optional timing-comparison slice. Page errors, live responsiveness, new collectors, automatic reload, extension-state changes, resource/network analysis, history/export, new targets, and the Rust companion require separate decisions.

## Primary references

- [Runtime messaging](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/runtime/sendMessage) reaches listeners across extension pages. This design avoids broadcasting timing payloads through that mechanism.
