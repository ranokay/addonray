The user confirmed this concrete plan after all nine design answers, including Firefox isolated execution, Chrome page-side execution, the 1 KiB summary bound, and the measured 5 ms p95 synchronous-operation budget. Essential source/control/cleanup feasibility must pass before product wiring; a failed essential gate requires a revised plan. Independent static planning review found no unresolved material issue after clarifying the counting deadline and distinguishing documentation, fixture observations, and unqualified production gates. The reviewer ran no browsers or tests. Production code and its control boundary still need their own later independent review.

## Problem and result

Timing comparisons describe document loading but do not describe JavaScript errors while a user reproduces a broken interaction. Add a deliberate, bounded page-error check for two top-frame event kinds: uncaught JavaScript error events and promise rejections that are unhandled when observed. Return counts and the completion reason, without raw error information or an extension-blame verdict.

Each check has a fresh separate tab and one attempt at a time. The popup chooses the original source tab; the check tab owns consent, Start, Stop, the final summary, and reset. It is independent of existing inventory/timing investigations. Nothing is collected merely by opening a check, retaining consent, or changing tabs.

## Selected user flow

1. Open AddonRay's toolbar popup on the source page and choose New page-error check. Bind the source's numeric tab ID and verified normal-window classification without reading its URL/title. Open a fresh check tab, with no source identifier in its URL.
2. Read the scope and privacy explanation, then press Start in that check tab. Request optional scripting access from this gesture. Opening the check does not start observation. The document loaded in the original tab when installation executes supplies this attempt; exact click-time document identity is not promised.
3. Return to the source through the browser's tabs and reproduce the interaction. Observe only future events in that top-frame document, for a 30-second window or until 200 events total. Show an observing state, without live counter updates. AddonRay never reloads, changes extensions, or chooses a different source.
4. Press Stop to finish early and keep the confirmed partial counts. Otherwise finish at the duration or event limit. Show each event-kind count, total, scope, and a fixed completion reason. A count is a notification observed during this interval, not a unique underlying defect or a console history.
5. If the source reloads, leaves its document, closes, or fails, show interrupted/unavailable rather than a successful zero. A same-document app view change does not create a new document; no URL or navigation history is collected to classify it.
6. Start over erases the final result before another explicit Start on the original source tab. Clear cancels and discards. Closing, reloading, or unloading the check tab discards its data. No history, restoration, comparison attachment, or export is added.

## Candidate architecture and required feasibility

Keep the existing timing collector unchanged. Add a separate check owner/state model, fixed summary validation, and browser adapter. Reuse browser-context labels and the existing permission explanation style. The new unlisted check entry point owns its in-memory state and permission listener; no background or storage owner is introduced.

Launching a data-bound check is different from the existing unbound New investigation action. Candidate bootstrap creates the check tab inactive, waits only for that own document's bounded readiness, binds the original source through a verified own-view endpoint, and activates it after acknowledgment. Source IDs never enter a URL. It must fail closed if the popup disappears or the target reloads during handoff. This sequence remains a browser-feasibility gate, not a working product claim.

The observer should use the same minimal counting logic with the target-specific world selected by a closed browser context. [ADR 0004](../adr/0004-page-error-execution-worlds.md) records the accepted execution choice and its trust limit. A candidate isolated supervisor/control connection associates one source frame and one check attempt with the visible owner. Owner closure or revocation must stop through that already established connection, because a fresh scripting call after access loss or document replacement is not a reliable cleanup mechanism. Chrome's page-side observer needs a narrow, validated control boundary; page-visible tokens are not authentication secrets. The control path may stop its own observer and return fixed counts, never request browser actions or carry page code.

This control design is still a candidate. Basic world-local Stop in a host-granted fixture does not qualify production owner-close or permission-revocation cleanup. If the mechanism cannot satisfy those gates with the agreed permissions and privacy boundary, stop and revise the plan with the user before implementation.

## Observed preliminary API evidence

Seven scratch checks passed on each of Firefox 140.0, Firefox 153.5.1esr reported as 153.5.1, Firefox 158.0.1, and Chrome for Testing 156.0.8078.47/macOS arm64. Drivers were geckodriver 0.37.1 and matching ChromeDriver 156.0.8078.47. All reports identify source 93f938e with dirty planning documents and successful browser/server cleanup. Raw files and the source-hash summary are in ignored `.scratch/page-error-feasibility/`.

The named host-granted local fixture generates exceptions/rejections through its own HTML button handlers, not driver-script callbacks. Page-owned positive controls saw prior events; later observers counted only the newly triggered pair. Firefox isolated and MAIN observers each saw one event of each kind. Chrome MAIN saw both; Chrome isolated saw neither. This supports the proposed world split for these tested cases, not blanket error coverage.

The MAIN candidate excluded a plain console call and failed image, retained partial counts on explicit Stop, removed listeners before subsequent page events, stopped at a three-event cap during a sixteen-event flood, and returned fixed count-only payloads without reading a rejection-object sentinel getter. New-document navigation fulfilled with a navigation reason and the replacement document lacked the old observer. A product must map that outcome to interrupted.

These short timers and three-event limits do not qualify the proposed production window/cap. Direct fixture stop handles are not a production bridge. No product code, actual activeTab path, native consent/UI, owner-close/revocation cleanup, hostile-page robustness, private context, restrictive CSP, BFCache restoration, hosted OS, or new-collector overhead is qualified yet. Initial setup failures and corrections are retained in the research directory.

1. Record the accepted execution-world decision and independent planning review, then confirm shared understanding including proposed result/overhead budgets.
2. Prove the source bootstrap and control/cleanup boundary with disposable fixtures before wiring the product. Record authority and gaps. Revise scope with the user if an essential gate fails.
