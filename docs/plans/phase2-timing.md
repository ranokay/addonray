# Phase 2 page-timing snapshot

Status: approved for implementation, testing, independent review, and signed private delivery on 2026-10-23. The user chose page timings first, the existing popup action/lifetime, current-document load observations without reloading or recording, the three milestones below, and original-tab targeting at collection time. [The interview](../decisions.md#phase-2-timing-interview) records those choices and final shared-understanding confirmation.

Independent planning review found no material issue in the scope, data boundary, zero/missing semantics, current lifecycle, feasibility sequence, or overhead proposal. Subsequent production-code and probe reviews found no actionable issue. Those reviews did not run tests or browsers; observed qualification remains separate.

## Problem and result

The page probe currently reports document readiness and supported performance entry types. It provides no actual loading measurements. This slice extends that deliberate action with three recorded milestones for the top-level document currently loaded in the selected tab.

| Display label           | Browser value                                           | Meaning                                                                                                                                            |
| ----------------------- | ------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| DOM content loaded      | Navigation entry `domContentLoadedEventEnd`             | Elapsed milliseconds from navigation start until the document's DOMContentLoaded handlers finish.                                                  |
| Load event completed    | Navigation entry `loadEventEnd`                         | Elapsed milliseconds from navigation start until the document's load handlers finish. This does not prove all future content or work has finished. |
| First content displayed | Paint entry named `first-contentful-paint`, `startTime` | Elapsed milliseconds from navigation start until the first qualifying text/image content is painted, when reported.                                |

These are recorded milestones, not the time spent collecting the snapshot, current responsiveness, measured extension overhead, or proof of a conflict. Results can reflect the network, caches, page work, browser state, and extension interactions. The tool does not identify a responsible extension or assign a speed score.

## User flow

1. Open the existing popup on the page to inspect. Opening collects nothing. The page section explains that its action reads readiness, supported types, and three loading milestones without collecting the URL or page content.
2. Choose the existing page-inspection action. Bind the selected tab and start optional scripting consent in the same gesture, using the current permission path. Retained consent never starts a capture automatically.
3. Read the top frame once in the default isolated world. If the original tab navigated while consent was open, read the document loaded there when execution runs. The browser may reject access after navigation. Never select a replacement tab or automatically retry.
4. Display readiness, existing support information, and the three explained milestones. Each measurement is an elapsed time since navigation began, with a consistent millisecond label. Unavailable or unrecorded values are explicit.
5. A later deliberate inspection replaces the previous page result, using the existing session/cancellation rules. Clear, relevant permission revocation, or closing the popup removes it. No results enter an investigation tab.

## Data and implementation boundaries

Extend the existing page-observation contract and injected collector, its external-response validation, and the page-result rendering. Reuse the current session for cancellation and permission listeners. Keep the adapter browser-neutral and pass the current browser context into explanations/errors as today. Do not alter the comparison state owner or add coordination between documents.

Keep collector code self-contained for browser serialization. Feature-detect the timeline methods and read only approved fields. Missing support and missing entries remain unavailable; native event-end zero is unrecorded. A valid fractional or zero paint measurement remains numeric. Do not use truthiness to decide whether a timestamp exists. Treat all browser-returned page results as untrusted and minimize them again before publication.

The UI labels describe the end of the named event handlers, not their processing duration. Do not subtract event start from event end for these milestones. No date or absolute timestamp is needed. A short limitation note should explain that same-document navigation and restored pages can expose original loading milestones, and that browser clock precision can reduce numeric detail.

## Verification sequence and stop conditions

1. Add focused feasibility probes and establish actual isolated-world access first. Keep fixture authority separate from the product. Probes use disposable profiles and controlled pages, and record dirty iteration honestly.
2. Implement the narrow contract/collector/UI with tests for event-end zero, measured fractional/zero paint, absent APIs/entries, invalid values, unknown extra fields, consent, target binding, duplicate-action guards, later captures, Clear, revocation, and popup lifetime. Check metadata sentinels in the raw returned object to prove URLs/content are excluded before extension retention.
3. Measure overhead on controlled pages. Report first-call and sequential-sample results separately from injection latency. Preserve the measuring method in the repository's browser checks; keep raw samples local. Do not claim the current supported-type probe already qualifies timing access or overhead.
4. Independently review permission/data boundaries, measurement wording, zero/missing handling, lifecycle, and evidence integrity. Fix material findings. Run all required gates, sign the implementation, then collect clean committed browser, source-rebuild, native, and hosted evidence.
5. Record exact revisions, artifacts, methodology, observations, failures/fixes, and remaining qualification gaps in a dated evidence document. Update the resumption checklist and push signed evidence to the existing private repository.

Stop after this popup snapshot slice and its recorded qualification. Performance comparisons, live responsiveness, page errors, mutation counts, automatic reload, resource/network analysis, history/export, other browsers/manifests, and the Rust companion require separate scope decisions.

## Research and limits

Research on 2026-10-23 used Context7's MDN content reference, official documentation, browser compatibility data, and browser source. This establishes a feasible API proposal; it does not replace installed-browser observations.

- [Navigation timing](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceNavigationTiming), [DOMContentLoaded event end](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceNavigationTiming/domContentLoadedEventEnd), and [load event end](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceNavigationTiming/loadEventEnd) define the recorded milestones. The navigation entry's name is the document URL, so whole-entry serialization violates the intended data boundary.
- [Paint timing](https://developer.mozilla.org/en-US/docs/Web/API/PerformancePaintTiming) and [current timeline reads](https://developer.mozilla.org/en-US/docs/Web/API/Performance/getEntriesByType) support an on-demand read of already reported paint data. First paint is optional; this slice uses first contentful paint and tolerates its absence.
- [Navigation compatibility](https://github.com/mdn/browser-compat-data/blob/main/api/PerformanceNavigationTiming.json) and [paint compatibility](https://github.com/mdn/browser-compat-data/blob/main/api/PerformancePaintTiming.json) document the core fields on the current baselines. Actual isolated-world access remains P2A-11.
- [Content-script environments](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Content_scripts#content_script_environment), [Firefox's window implementation](https://github.com/mozilla-firefox/firefox/blob/main/dom/base/nsGlobalWindowInner.cpp), and [Chromium's performance accessor](https://github.com/chromium/chromium/blob/main/third_party/blink/renderer/core/timing/dom_window_performance.cc) support testing the standard API through the isolated world before considering any additional mechanism.
- [Scripting target compatibility](https://github.com/mdn/browser-compat-data/blob/main/webextensions/api/scripting.json) places Firefox `documentIds` injection targets after the existing minimum. The approved contract is original-tab targeting at execution, not exact click-time document identity. [Chrome activeTab](https://developer.chrome.com/docs/extensions/develop/concepts/activeTab) and [Firefox activeTab](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/permissions#activetab_permission) still govern temporary access.
- [Back/forward-cache measurement](https://web.dev/articles/bfcache#performance_measurement) explains why navigation type alone does not establish a BFCache restore. This slice neither identifies restoration nor claims to measure a fresh load after it.
